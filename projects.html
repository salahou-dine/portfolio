Projet académique 2025 Équipe de 4

Système de prédiction de maintenance industrielle

Code source Rapport PDF

Problème adressé

Dans l'industrie manufacturière, les arrêts non planifiés d'équipements représentent des pertes significatives (estimées entre 5% et 20% de la capacité de production). L'objectif était de développer un système capable d'anticiper les défaillances à partir de données de capteurs IoT, permettant une planification proactive de la maintenance.

Contexte

Projet réalisé dans le cadre du module "Machine Learning Appliqué" (2ème année). Travail en équipe de 4 étudiants sur 8 semaines. Encadrement par un enseignant-chercheur spécialisé en systèmes industriels.

Données utilisées

Dataset public NASA Turbofan Engine Degradation Simulation (C-MAPSS). Environ 50 000 enregistrements de 21 capteurs sur 100 moteurs. Données de run-to-failure simulées avec différents modes de défaillance.

  • Variables : température, pression, vitesse de rotation, vibrations
  • Cible : Remaining Useful Life (RUL) - nombre de cycles avant défaillance
  • Prétraitement : normalisation, gestion des valeurs manquantes (< 2%)

Approche technique

Méthodologie CRISP-DM adaptée. Travail itératif avec plusieurs phases :

  • Analyse exploratoire : étude des distributions, corrélations entre capteurs, identification des patterns de dégradation
  • Feature engineering : création de fenêtres glissantes, calcul de tendances et statistiques sur fenêtres temporelles
  • Modélisation : baseline avec régression linéaire, puis Random Forest et XGBoost. Transformation du problème de régression (RUL) en classification binaire (défaillance < 30 cycles)
  • Validation : validation croisée temporelle (5 folds), test sur moteurs non vus pendant l'entraînement

Technologies utilisées

Python 3.10 Pandas NumPy scikit-learn XGBoost Matplotlib Seaborn Jupyter

Résultats obtenus

  • Précision de classification (seuil 30 cycles) : 87%
  • Rappel sur classe "défaillance imminente" : 82%
  • RMSE sur prédiction RUL : 18.3 cycles (baseline : 31.2)
  • Amélioration de 41% par rapport à la baseline linéaire

Limites identifiées

  • Données simulées : le comportement réel des capteurs industriels peut différer significativement
  • Modèle statique : pas de prise en compte de l'évolution des conditions d'exploitation
  • Seuil de 30 cycles arbitraire : nécessiterait une étude coût-bénéfice avec des données économiques réelles
  • Interprétabilité limitée de XGBoost pour les opérateurs terrain

Pistes d'amélioration

  • Intégration de modèles séquentiels (LSTM) pour mieux capturer les dépendances temporelles
  • Ajout d'un module d'explicabilité (SHAP) pour les décisions critiques
  • Test sur données réelles en partenariat avec un industriel
  • Développement d'une interface de visualisation pour les techniciens
Hackathon 2025 Équipe de 3

Détection de fraude bancaire sur données déséquilibrées

Code source

Problème adressé

La détection de fraude bancaire pose un défi classique en machine learning : les classes sont extrêmement déséquilibrées (< 0.2% de transactions frauduleuses). Les modèles naïfs atteignent 99%+ de précision en prédisant "non fraude" systématiquement, ce qui est inutile en pratique.

Contexte

Hackathon IA organisé par une école partenaire (48h). Défi proposé par une fintech locale. Équipe de 3 étudiants. Classement : top 5 sur 20 équipes.

Données utilisées

Dataset Kaggle "Credit Card Fraud Detection" (anonymisé par PCA). 284 807 transactions, dont 492 frauduleuses (0.172%). 30 features après transformation PCA + montant et temps.

Approche technique

  • Rééchantillonnage : comparaison SMOTE, ADASYN, undersampling, et combinaison SMOTE + Tomek links
  • Modèles testés : Régression logistique, Random Forest, XGBoost, réseau de neurones simple (2 couches)
  • Métriques : focus sur AUC-ROC, Precision-Recall, et F1-score plutôt que l'accuracy
  • Optimisation du seuil : analyse coût-bénéfice pour déterminer le seuil de décision optimal

Technologies utilisées

Python imbalanced-learn scikit-learn TensorFlow/Keras Pandas

Résultats obtenus

  • Meilleur modèle : XGBoost + SMOTE avec AUC-ROC de 0.98
  • Recall sur fraudes : 91% (seuil optimisé)
  • Precision : 78% - taux de faux positifs acceptable
  • Réduction estimée des pertes : 85% des fraudes détectées

Limites identifiées

  • Données anonymisées par PCA : pas d'interprétabilité métier
  • Pas de dimension temporelle dans le modèle (transactions indépendantes)
  • Coût réel des faux positifs non quantifié (friction client)

Pistes d'amélioration

  • Modèles de détection d'anomalies (Isolation Forest, Autoencoders)
  • Intégration du comportement utilisateur dans le temps
  • Système d'alerte avec niveaux de confiance pour revue manuelle
Projet personnel 2024 Solo

Dashboard d'analyse COVID-19

Code source Démo live

Problème adressé

Pendant la pandémie, l'accès à des données claires et actualisées était crucial. Ce projet visait à créer un tableau de bord interactif permettant de visualiser l'évolution de la pandémie avec des données mises à jour quotidiennement.

Contexte

Projet personnel réalisé pendant les vacances pour pratiquer la visualisation de données et l'intégration d'APIs. Environ 40 heures de travail sur 2 semaines.

Données utilisées

API COVID-19 Data Repository by Johns Hopkins CSSE. Données mondiales mises à jour quotidiennement : cas confirmés, décès, guérisons par pays et région.

Approche technique

  • Pipeline de récupération automatique des données via API REST
  • Nettoyage et agrégation des données (gestion des incohérences entre sources)
  • Visualisations interactives : cartes, courbes temporelles, comparaisons
  • Calcul d'indicateurs dérivés : taux de mortalité, moyennes mobiles

Technologies utilisées

Python Plotly Dash Pandas Requests Heroku

Résultats obtenus

  • Dashboard fonctionnel avec mise à jour automatique quotidienne
  • 5 visualisations interactives (carte mondiale, courbes, comparatifs)
  • Temps de chargement < 3 secondes
  • Partagé avec la communauté étudiante (~50 utilisateurs)

Limites identifiées

  • Dépendance à une source unique (fiabilité des données JHU)
  • Pas de cache : chaque visite recharge les données complètes
  • Interface non optimisée pour mobile

Pistes d'amélioration

  • Ajout de modèles prédictifs simples (extrapolation)
  • Intégration de données de vaccination
  • Mise en cache avec Redis pour améliorer les performances
